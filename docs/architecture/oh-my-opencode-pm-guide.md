# Oh-My-OpenCode 是怎么编排工作的？（给产品经理）

> **一句话**：Oh-My-OpenCode 把“一个会写代码的助手”升级成“一个带队的开发团队”：主会话里有一个“指挥官”（Atlas/Sisyphus），它不亲自写代码，而是把工作拆成小工单派给多个子会话里的“执行工程师”（子代理），再把结果验收、串起来，直到交付。

**更新时间**：2026-02-04  
**你关心的问题**：它怎么派工？怎么保证不中断？怎么跟 OpenCode 基座（新的单会话 orchestrator）共存？未来怎么复制成“律师插件”？

---

## 1) 两层产品：OpenCode 基座 vs Oh-My 插件

### OpenCode（基座）
可以理解为：
- 一个通用的聊天 + 工具执行平台（读文件、跑命令、改代码、跑测试等）
- 提供 session（会话）与 task（子会话/子任务）能力
- 新增了一个“单会话 orchestrator”（实验功能）：会在**同一个聊天窗口**里先做规划/证据补齐，并在需要时进入 fork 模式派发子会话执行

### Oh-My-OpenCode（插件）
可以理解为：
- 在基座上“加装一个多智能体编排系统”
- 核心价值：**计划→派工→验收→继续推进**的闭环，尤其适合大任务/多步骤/需要验证的任务

你提出的方向非常对：  
**基座是通用引擎**；Oh-My 是“专业编排插件”（目前偏编程领域），未来可以复制成律师插件/金融插件等。

---

## 2) 关键概念（用“团队协作”解释）

### 主会话（主聊天窗口）
- 就像一个“项目群/作战室”
- 指挥官在这里看全局、拆任务、验收结果

### 子会话（被派发的任务窗口）
- 就像一个“工单/子任务”
- 每个子会话有自己的执行环境（工具、上下文、日志），互相隔离
- 子代理在这里负责“真正动手做事”：写代码、修 bug、跑测试等

### 计划（Plan）
Oh-My 常用的工作方式是：
1) 先产生一个“计划文档”（一堆 checkbox）
2) 然后指挥官逐个 checkbox 派工执行

计划文件默认放在：
- `.sisyphus/plans/*.md`

### boulder.json（不中断续跑的“项目状态”）
为了让工作“断了也能继续”，Oh-My 会写一个状态文件：
- `.sisyphus/boulder.json`

里面记录：
- 当前执行的是哪一份 plan
- 哪些 session 参与过（方便后续自动续跑/恢复）

### delegate_task（派工按钮）
指挥官派工的主要工具就是 `delegate_task`：
- 你可以把它理解为：“创建一个子会话，让某个执行工程师开始干活”
- 它支持同步等待结果，也支持后台并行跑多个子任务

## 3) Oh-My 的典型使用路径（非常具体）

### 路径 A：简单问题（不需要编排）
例如：问一个概念、改一行配置、单文件小修。
- 直接在主会话问就够了

### 路径 B：复杂但想“可控、可验收”
例如：重构认证系统、做一次大规模迁移、加一个新模块并补齐测试。

常见流程：
1) 先用 Prometheus（规划者）把问题问清楚并输出计划（plan）
2) 再用 `/start-work` 开始执行计划
3) Atlas（执行指挥官）逐条 checkbox 派工给子会话（子代理）
4) 每个子会话完成后，Atlas 在主会话验收、跑验证、决定下一步

为什么这种好用？
- 复杂工作最大的风险是“漏项”和“没验证”。计划+验收让输出更稳定。

### 路径 C：复杂但你很懒（ulw / ultrawork）
适用于“你不想把上下文讲清楚”，让系统自己先探索，再给方案。

## 4) 关键机制：为什么它能“逼着团队把活干完”

这里有两个“产品级强约束”：

### 4.1 指挥官不允许直接写代码（除非在 .sisyphus 内）
指挥官的职责是：派工+验收，而不是亲自改代码。

这不是嘴上说说，Oh-My 通过 hook 做运行时提醒/拦截：
- 如果 Atlas 在主会话直接 `Write/Edit` 改业务代码，会被强提醒“你是指挥官，不是执行者”
- 从而把手上工作推回到“子会话派工”这个正确路径上

### 4.2 自动续跑（直到 checklist 全勾完）
当系统发现：
- 当前 plan 还有未完成 checkbox
- 且当前 session 处于 idle

它会自动注入“继续执行剩余任务”的提示，推动工作不停下来（减少“做一半就停”）。

## 5) 与 OpenCode 基座单会话 orchestrator 是否冲突？怎么兼容？

你观察到的点非常关键：  
**OpenCode 基座**也开始具备 orchestrator（单会话内规划 + fork 派工）能力，  
**Oh-My 插件**也具备 orchestrator（多会话派工 + 验收推进）能力。

如果两边都“自动派工”，就会出现我们一直说的：
- **双重派工**：同一个需求被派成两份子会话/两组执行
- **方向盘冲突**：两个指挥官都觉得“我负责派工”，导致体验混乱、成本上升

### 5.1 兼容原则（产品视角）
我们希望达成的产品体验是：
- **一个窗口里先把问题拆清楚**（快速规划/补齐证据缺口）
- **真正动手时再派子会话**（隔离、安全、可审计）
- 并且当用户安装 Oh-My 时：**Oh-My 负责“派工与多会话协作”**，基座 orchestrator 负责“单会话内的快拆与提示”

这对应到基座里一个关键开关：`OPENCODE_ORCHESTRATOR_FORK_STRATEGY`。

### 5.2 最推荐的共存设置（当前阶段）
当你希望 **Oh-My 接管派工（主会话 → 子会话）** 时，推荐：

```bash
export OPENCODE_EXPERIMENTAL_ORCHESTRATOR=1
export OPENCODE_ORCHESTRATOR_FORK_STRATEGY=suggest
```

它意味着：
- 基座 orchestrator 仍然可以在“单会话里”做快速分析/计划/证据提示
- 但当它判断需要 fork 派工时，只会给出 **“建议派工”**（suggest），不会自己自动创建子会话
- 真正派工由 Oh-My 来做（更符合多会话编排插件的定位）

补充说明（实践建议）：
- 这些环境变量最好在 **启动 OpenCode 之前** 就设置好（最稳妥），避免运行中变更不生效的情况。

### 5.3 Oh-My 的提示开关（防止用户配错）
Oh-My 目前提供一个**可选的**兼容提示开关（默认关闭，不会打扰老用户）：

```jsonc
{
  "experimental": {
    "opencode_orchestrator_compat": { "enabled": true }
  }
}
```

开启后：当系统检测到“基座 orchestrator 开启 + forkStrategy 仍是 auto/缺省”时，会在启动时给一次 warning，提醒你改成 `suggest`。

## 6) 这套机制为什么适合“未来复制成律师插件”？

你说的“复制 oh-my，换 prompt/子代理 prompt，变成律师插件”，本质是在做一件事：
- **把编排引擎复用**（计划、派工、验收、续跑、后台并行、tmux 可视化）
- **把领域知识替换**（提示词、分类体系、默认 skills、工具 allowlist、合规策略）

在 Oh-My 的实现里，这两类东西大致分布为：

### 6.1 更像“引擎”的部分（尽量不动，复制也能直接用）
- 派工工具与会话生命周期：`delegate_task` / background tasks
- boulder 状态续跑：`.sisyphus/boulder.json` + 自动续跑 hooks
- 通用工具：grep/glob/lsp/ast-grep、session-manager、tmux
- 质量约束：TDD、强制验收、不要相信自报完成

### 6.2 更像“领域包”的部分（律师插件主要改这里）
- 各个 agent 的系统提示词：例如 Prometheus/Atlas/Sisyphus/Junior
- delegate_task 的 category 分类（比如编程领域是 quick / visual-engineering 等）
- 默认推荐 skills（比如律师领域可能更偏“法规检索/证据链/引用格式/隐私红线”）
- “可用工具与权限”策略（律师领域可能禁用写文件/跑命令，或强制引用与证据存档）

这也是为什么我们现在的策略是：
- 先把 **OpenCode 基座 orchestrator** 做成稳定的通用能力与契约
- 再把 **Oh-My** 做成可复用/可复制的“领域编排插件模板”

## 7) 你可以怎么决策（给产品的可选项）

如果你要对外解释“我们到底怎么工作”，可以用一个简单的分工：

### 分工一句话
- **OpenCode 基座 orchestrator**：一个窗口里快速把问题拆清楚（低成本、快、稳定）
- **Oh-My 插件**：需要动手时，派到多个子会话让“执行工程师团队”并行干活（隔离、可审计、可验收）

### 推荐默认
当用户安装 Oh-My 且要用多会话协作时：
- 基座 forkStrategy 走 `suggest`
- Oh-My 负责派工

后续我们要做的“完全兼容”升级方向（先设计再实施）是：
- 让 Oh-My 能更主动地“消费”基座 orchestrator 的输出（计划/证据指针）
- 让两边协作更顺滑，但仍然保持职责边界清晰（不抢方向盘）
